# 產品需求 {#purpose}

本檔是功能的上游契約。模糊點子先寫進這裡，經使用者確認之後，才進 `docs/00-ui-spec.md` 與 `docs/00-architecture.md`。本檔決定業務範圍，不決定類別怎麼拆，也不修改程式。

專案名稱沿用 `docs/00-architecture.md` 的 `<PROJECT_NAME>`。第一個真實需求進來時，把下面標成「尚無」的章節換成該需求的內容。每個功能點在自己的標題寫上 `{#feat-<english-slug>}`，slug 用英文小寫與連字號。登入這類名稱只是 slug 範例，本範本沒有該功能，所以這裡不放對應標題。

#REF: [00-architecture.md#upstream] - 確認本檔之後才允許進入分層設計
#REF: [00-architecture.md#system-boundary] - 業務邊界會寫進系統邊界，拆層仍留在架構文件
#REF: [00-ui-spec.md#screens] - 會對人顯示的功能要在 UI 規格找到畫面；純後端由該節標註略過

## 業務目標 {#goals}

尚無已確認的產品目標。

寫下這個系統為誰、把哪一件事做成、怎樣算成功。成功條件要能觀察。實作方案留到架構文件。

## User Stories {#user-stories}

尚無。

每一則寫成：身為某個角色，要做某一件事，以便得到某個業務結果，並註明對應的 `{#feat-<slug>}`。slug 必須與功能標題上的錨點相同。

## 功能清單 {#features}

| 錨點 | 一句話 | 狀態 |
| --- | --- | --- |
| 尚無 | — | 等待第一個需求 |

錨點寫在功能章節的標題上，一個功能點一個 id。尚無功能時不預建空章節。架構文件與 UI 規格只准 `#REF` 到標題上已經存在的 id。

新增功能時，在本節表格加一列，並另開一節寫輸入與輸出、邊界條件、失敗處理。業務語言即可，不寫類別名稱、資料表或 HTTP 狀態碼。

## 輸入與輸出規格 {#io}

尚無。

每個功能要寫明輸入來源、欄位、必填、輸出給誰、成功時看得到什麼。

## 邊界條件 {#edge-cases}

尚無。

寫極值、空值、重複提交、權限不符、同時發生的操作。每一條要能對上一個功能錨點。

## 失敗處理 {#failures}

尚無。

寫使用者看得到的失敗，以及業務上不能發生的事。例外類別與狀態碼留到架構文件。

## 確認閘門 {#gate}

本階段禁止建立或修改 `src/`、`tests/`、`db/`。

進入架構設計之前，使用者要先確認本檔。有畫面時，確認本檔之後先完成 `docs/00-ui-spec.md`，再進架構。純後端在 UI 規格標註「純後端專案，略過 UI 規格」。

接受語句是「確認，可以設計」。這句話只進入文件。修改程式仍要等架構文件被「確認，可以實作」。

#REF: [00-ui-spec.md#gate] - 畫面階段使用同一句確認，同樣不允許改程式
