# 安全開發與 PR

## 何時使用 {#when}

使用者要求在公司既有專案新增功能或修 Bug。先寫修改設計，確認後才改程式。

#REF: [../../../AGENTS.md#do-no-harm] - 計畫外不重構、不改無關程式
#REF: [../../../AGENTS.md#security] - 沿用公司的 Logger、秘密處理與 Git 規範
#REF: [../01-repo-onboarding/SKILL.md#local-style] - 先沿用盤點到的目錄、命名與錯誤處理

## 修改設計 {#plan}

動工前先讀目標附近的實作與測試，以及 `docs/catchup/` 裡已有的相關筆記。不要套用另一套 MVC 範本。

用下面格式寫短設計。可以先寫在回覆中；使用者接受後，把同一份內容存成 `docs/catchup/change-<english-slug>.md`，方便之後追溯。確認前不要寫應用程式碼。

```markdown
# 修改設計：<一句話> {#plan}

## 問題或目標 {#goal}

使用者要的結果，以及現在程式實際做的事（附路徑）。

## 修改計畫 {#approach}

模仿哪一個既有檔案的風格。準備改哪些符號。不改哪些鄰近程式。

## 影響範圍 {#impact}

| 路徑 | 變更 | 為什麼必須動它 |
| --- | --- | --- |

## 行為與風險 {#risk}

- 誰的舊行為會變：
- 資料或遷移：無，或沿用公司既有遷移工具的檔名
- 設定或秘密：無，或新增的變數名稱（不含值）
- 日誌：沿用哪一個既有 Logger 與錯誤型別

## 測試 {#tests}

沿用哪一個既有測試檔的位置與命名。準備補的案例。

## 關聯 {#refs}

#REF: [相對路徑#符號] - 這次要改的現況
```

影響範圍要含測試檔。只為了格式一致而會碰到的檔案不放進表內，也不要改它們。

## 確認閘門 {#stop}

設計送出後停止。使用者明確說「確認，可以改」或「按這個計畫改」之後才實作。

「好」「繼續」「你看著辦」不算確認。計畫不完整，尤其影響範圍有「可能還會改到」這種未定路徑時，先補完再問，不要邊做邊擴。

使用者只接受計畫的一部分時，只改接受的路徑。

## 實作 {#implement}

1. 打開影響範圍裡最接近的既有檔案，對齊縮排、命名、錯誤處理、匯入順序與註解密度。
2. 只改表格裡的路徑。格式化工具若會改寫整個檔案，先看公司是不是本來就對這些檔案這樣做；會掃到無關差異時，縮小範圍或在回覆說明，不把整檔重排混進變更。
3. 設定與秘密走公司既有管道。不把值寫死，不把值寫進 `docs/catchup/`。
4. 補測試。測試放在公司已經在用的目錄，使用同樣的執行器與命名。至少覆蓋：缺陷或新行為的成功路徑、文件裡寫到的失敗路徑、以及一個證明舊行為仍在的鄰近案例（若該行為有既有測試，更新斷言而不是複製一整份）。
5. 用公司 CI 裡的同一條測試指令執行你碰到的測試。指令會改寫檔案時，先告訴使用者再執行。

實作中發現計畫漏了檔案：停止修改，把新路徑補進設計，再次確認。已經改到一半的檔案在回覆中列出來。

## PR 描述 {#pr-template}

先讀最近的 Pull Request 或公司範本。公司有固定標題就沿用，並把下列資訊放進去。公司沒有範本時使用：

```markdown
## 變更摘要

這次改變的使用者可觀察行為。

## 影響評估

- 改到的路徑：
- 沒改但讀過、確認不用動的鄰近模組：
- 資料遷移：
- 設定變更：
- 相容性：舊呼叫端是否仍可運作

## 測試步驟

1. 執行的指令：
2. 成功時應該看到：
3. 失敗案例應該看到：
4. 手動點選或呼叫的路徑（若有）：

## 關聯

- 修改設計：docs/catchup/change-<slug>.md（私人筆記，不在公司遠端）
- 程式：
```

另外附上一段可直接貼到提交訊息的文字。提交訊息的語言、`type` 與 `scope` 以最近 30 筆 `git log` 的多數寫法為準，並在 PR 描述上面用一行註明你模仿的是哪一種。看不出多數寫法時，把兩種候選交給使用者選，不自行提交。

預設不執行 `git commit`、`git push`、開啟遠端 PR。使用者明確要求時才做，而且提交內容不得包含 `AGENTS.md`、`.agents/`、`docs/catchup/`。提交前用 `git status` 核對。

## 完成條件

回覆包含：已確認的設計路徑、實際修改的檔案、測試指令與結果、PR 描述。實際修改的檔案與影響範圍不一致時，先說明多出來的原因；那代表閘門沒守住，要停下來補正，而不是在 PR 裡把它說成小改動。
